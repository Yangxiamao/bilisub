## 1. 背景与目标

- 我在 B 站网页（Chrome）上看中文视频，很多视频没有 CC 字幕，也没有 B 站 AI 字幕。
- 目标：做一个 Chrome 扩展。遇到没有字幕的视频时，我手动开启它，它用 Gemini API 把中文语音**听写**成中文字幕（不翻译），并显示在播放器上，全屏时也能显示。
- 我的电脑性能一般，不能在本地跑大型语音识别模型。识别必须走云端（我有已充值的 Gemini API）。
- 测试视频：<https://www.bilibili.com/video/BV1VXGL6KE9D/>。48 分钟游戏实况，解说夹杂炮火声，没有字幕。

## 3. 核心架构（推荐方案，需要 Phase 0 验证）

### 3.1 为什么不用 tabCapture

字幕本质上要在时间轴上显示：每条有开始和结束时间，播放到那一刻才显示。实时录音要等声音播完才拿到音频，再等 Gemini 返回结果时，那句话早已播完，字幕要么错过、要么滞后。而 B 站是点播，音频文件可以提前获取，所以改为**在播放位置前方提前转写**。这样字幕可以与画面同步，也才能放进官方字幕模块。

### 3.2 处理流程

```
获取当前视频（bvid、cid）的 DASH 音频信息
  → 按时间范围分段拉取音频（Range 请求）
  → 转成 Gemini 可接受的格式
  → 调用 Gemini generateContent 转写（返回带时间戳的结果）
  → 换算成视频绝对时间、拆分成短字幕、与相邻片段去重
  → 写入字幕轨道（方案 A：官方字幕模块；方案 B：自绘）
  → 写入本地缓存
```

- 调度围绕 `video.currentTime`：保持 [当前位置, 当前位置 + 预读缓冲] 区间已转写。
- 暂停时补满缓冲后停止。
- 拖动进度条时，取消不再需要的请求，从新位置开始；已经转写过的区间直接复用。
- 倍速播放时，缓冲按视频时间计算，必要时增加并发。
- 开启或拖动后的第一段用较短的切片（例如 10～15 秒），以缩短等待时间；之后用较长的切片（例如 30～60 秒）。具体长度由 Phase 0 的实测决定。

## 4. Phase 0：可行性验证

每项验证都要写清楚：目标、做法、成功标准、失败后的备选方案。完成后向我汇报结果，再进入正式开发。

### S1. 获取音频流
- **思路**：优先被动获取播放器自己的数据，比如读取页面的 `window.__playinfo__`，或在页面上下文（MAIN world）拦截播放器请求播放地址的响应。尽量避免自己调用需要 wbi 签名的接口。
- **要点**：
  - 选码率最低的 AAC 音轨。
  - 处理 CDN 地址过期（地址里带有效期参数）。
  - 切换分 P 或合集连播（单页应用跳转）时，能拿到新视频的音频信息。
  - 确认 Range 请求的 CORS 和 Referer 是否有问题：从页面上下文请求，或从扩展后台请求加 declarativeNetRequest 设置 Referer，二选一。
- **成功标准**：能稳定拿到测试视频任意时间段（例如 10:00～10:30）对应的音频数据。

### S2. 音频切片与格式
- B 站 DASH 音频是 fMP4（m4s）。需要按时间切出片段，转成 Gemini 能接受的格式。
- **候选做法**：
  1. 利用 sidx 索引，把 init segment 加若干 fragment 直接以 `audio/mp4` 发送；
  2. 解码（decodeAudioData，或 WebCodecs 加 mp4 解封装）后重编码成 16kHz 单声道 WAV、FLAC 或 Opus。
- **注意**：
  - MV3 的 service worker 里没有 AudioContext，需要 offscreen document 或放在页面侧处理。
  - Gemini 会把音频降采样到约 16 Kbps，**token 只按时长计费（约 32 token/秒）**，码率不影响费用，只影响上传大小。
  - inline 请求总大小不能超过 20MB。
- **成功标准**：任意一段 30～60 秒的音频能被 Gemini 正常识别，切点误差不超过 0.1 秒。

### S3. Gemini 转写质量、时间戳与费用
用测试视频中的几段（包括炮火声密集的段落）比较以下两类方案。以下信息截至 2026 年 11 月，模型 ID、价格和参数以实施时的官方文档为准。

**候选 1：通用模型加提示词（`generateContent`）**
- `gemini-3.5-flash-lite`：GA，2026 年 7 月发布。支持音频输入，音频和文本输入同价 $0.30/百万 token，输出 $2.50。思考级别可选 MINIMAL、LOW、MEDIUM、HIGH，默认 MINIMAL。
- `gemini-3.6-flash`：高精度备选。输入 $0.75，输出 $3.75；从 2027 年 1 月起涨到 $1.50 和 $7.50。
- （`gemini-3.1-flash-lite` 已被 3.5 Flash-Lite 取代，除非 3.5 Flash-Lite 有问题，否则不用测。）
- 时间戳靠提示词让模型输出（片段级），精度需要实测。
- 思考级别设为最低。思考 token 按输出计费，转写任务用不到思考。
- 比较输出格式：结构化 JSON（responseSchema）和紧凑文本（例如每行 `起始秒|结束秒|文字`），评估稳定性和输出 token 量。

**候选 2：专用转写模型 `gemini-3.5-transcribe`**
- 走 Interactions API（`POST /v1beta/interactions`）。文档示例是先用 Files API 上传音频，再在请求里引用；请确认是否支持 inline 音频。如果每段都要先上传，要评估额外的延迟。
- 支持「Mandarin Chinese (Simplified)」（`cmn-Hans-CN`），有自动语言检测。
- 可以输出**词级时间戳**，对字幕同步和断句很有价值。但文档提醒，开启时间戳可能降低准确率；开启时间戳或说话人分离后，单次最长 30 分钟。
- 支持自定义词表（例如从视频标题、标签中提取游戏术语），但**不能和词级时间戳同时使用**。需要比较：A) 词级时间戳；B) 词表加片段级时间对齐。
- 价格约 $0.005/分钟（输入 $0.003/分钟，输出 $0.002/分钟），大约是 3.5 Flash-Lite 的 3～4 倍。48 分钟视频约 $0.24，仍然很便宜。
- 不要用 `gemini-3.5-transcribe-live`（Live API）。约 $0.009/分钟，而且提前转写方案不需要实时流。

**评估内容**
- 识别准确率：由我抽查，你提供方便对照的输出。
- 时间戳误差。
- 有没有幻觉，比如在只有炮火声的地方编造文字。
- 首段字幕出现所需的时间（端到端延迟）。
- 每分钟音频的实际费用。

**成功标准**：默认方案在测试视频上我认为可读，时间误差在 ±1 秒以内，开启后 20 秒内出现第一条字幕。默认模型最终由数据决定。如果两类方案差距不大，选便宜的；如果专用转写模型明显更准，选它。两者都保留为可切换选项。

### S4. 注入 B 站官方字幕模块
- **调研**：3.x 播放器的字幕列表从哪个接口来；字幕内容的格式（BCC JSON，大致是 `body: [{from, to, content}]`，以实际代码为准）；AI 字幕轨道是怎样表示的。
- **尝试**：在 MAIN world 拦截相关的 fetch 和 XHR，往字幕列表里加一条「Gemini 字幕」轨道，并在播放器请求这条轨道内容时返回我们生成的数据。
- **关键难点**：转写是增量进行的，需要在**不打断播放**的前提下持续更新轨道内容。可能的做法包括重新触发加载、调用播放器内部方法等，需要调研。
- 已知参考：B 站常用字幕脚本「Bilibili CC字幕工具」写明，它的本地字幕加载功能在 3.x 播放器上已失效。所以这条路没有现成做法，需要你从播放器代码入手。
- **成功标准**：
  - 官方字幕菜单里出现这条轨道；
  - 新转写的内容能在 1～2 秒内生效，播放不卡顿；
  - 普通播放、网页全屏、全屏三种模式都能显示；
  - 字号等 B 站字幕设置对它生效。
- **失败时**：采用方案 B。在播放器的字幕容器（或全屏元素）内插入自己的元素，复用 B 站字幕的 CSS 类名或样式，尽量读取 B 站的字幕样式设置。在计划里说明你判断失败的依据。

## 5. v1 功能需求

### 5.1 入口与状态
- 入口：扩展图标弹窗，以及播放器上的一个开关按钮（你评估放在哪里最合适，例如控制栏或字幕菜单附近）。
- 显示简洁的状态：转写中、缓冲进度、出错原因。
- 合集连播或切换分 P 时，停止旧视频的任务。**是否对下一个视频自动继续由设置决定**，默认在同一标签页内继续，因为看合集时反复手动开启很麻烦。

### 5.2 转写内容规则
- 转写**所有清晰的人声对白**，包括解说和游戏角色台词。
- 不转写歌词或 BGM、音效，不加 [笑声]、[炮火声] 之类的标注。
- 听不清的部分直接跳过，**不要编造**。
- 输出简体中文。英文单词、游戏术语和专有名词按原样保留。

### 5.3 字幕格式
- 每条不超过约 20 个汉字，长句按语义拆分成多条，时间按比例分配，或请模型直接输出短句。
- 保留逗号、问号、感叹号，去掉句末句号，风格接近 B 站 AI 字幕。
- 去掉相邻片段重叠部分产生的重复字幕。

### 5.4 缓存
- 用 IndexedDB 缓存。key 包含 bvid、cid、模型 ID 和提示词版本，并记录已覆盖的时间区间。
- 重看时直接使用缓存，不再调用 API。
- 设置页可以清空缓存。

### 5.5 设置页
- API Key、模型选择、预读时长、连播时是否自动继续、调试模式（日志和导出）、清空缓存。
- 首次使用说明：费用估算（例如每小时音频大约多少钱）、音频会发送给 Google，并链接到 Gemini API 的数据使用条款。

### 5.6 错误处理
- Key 无效、限流（429）、网络错误、服务端 5xx：用指数退避重试，在播放器内轻量提示，不弹窗打扰。
- B 站播放地址失效：自动重新获取。

## 6. Gemini 调用要求

- 用非实时接口：通用模型走 `generateContent`，专用转写模型走 Interactions API。**不用 Live API**。Live API 的音频单价更高，而且提前转写方案不需要实时流。
- 两类方案（通用模型加提示词、专用转写模型）在代码里抽象成同一个「转写器」接口，输入音频片段和上下文，输出带时间戳的字幕条目，方便切换和比较。
- 模型 ID 放在配置里，可切换。
- 通用模型的思考级别设为最低。
- 降低费用的措施：
  - 关闭或最小化思考；
  - 精简输出格式；
  - 本地缓存；
  - 只转写预读缓冲范围内的内容，不一口气转写整部视频；
  - 提示词保持精简。
- **可选实验**（默认关闭，在 S3 中顺带评估是否值得做）：
  - 用轻量 VAD 跳过长时间没有人声的片段；
  - 把音频加速 1.25～1.5 倍以减少计费时长，需要评估对准确率的影响。
- 并发和限流：同时进行的请求数有上限，并且可以配置。
- API base URL 写成常量或配置项，方便以后改用代理，但 v1 不做 UI。

## 7. 技术栈与工程

- **WXT + TypeScript + Manifest V3**，不引入 React 等 UI 框架，设置页和弹窗用原生 DOM。选 WXT 的原因：维护活跃、基于 Vite、方便处理 MAIN world 脚本和多个入口、以后上架打包也简单。如果你认为有更好的选择，请说明理由。
- 职责划分由你设计，但要考虑：
  - MAIN world 脚本：拦截播放器的网络请求、操作播放器；
  - isolated content script：调度和 UI；
  - background service worker：Gemini 调用、跨源请求；
  - offscreen document：音频解码，如果需要的话。
- 权限最小化（为以后上架做准备）。
- API Key **不写进代码，不提交到 git**。开发用的评估脚本从 `.env` 读取 Key，`.env` 加进 `.gitignore`。
- 调试模式：可以导出音频片段、Gemini 原始请求和响应（不含 Key）、生成的 SRT。
- 测试：
  - 纯逻辑部分写单元测试，比如时间戳解析、字幕拆分、区间合并、去重；
  - 端到端以手动测试清单为主；
  - 如果要用 Playwright 自动化，注意 Playwright 自带的 Chromium 没有 AAC 和 H.264 解码，需要改用本机安装的 Chrome（channel: 'chrome'）。
- 小步提交 git，每个 Phase 结束时能正常运行。
